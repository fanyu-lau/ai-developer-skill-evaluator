# PawSkill — AI Developer Skill Evaluator

PawSkill is an evidence-first prototype for helping a developer understand how they work with AI coding tools. It combines verified engineering evidence with privacy-minimised local activity signals to produce:

- a dashboard with competency scores and evidence timeline;
- a Claude Code history summary;
- a GitHub pull request delivery-practice summary, optionally correlated with Claude history;
- an optional coaching report generated by Codex CLI or Claude CLI;
- flexible engineering work-style archetypes with animal avatars and tiers.

It is designed for self-reflection and development. It is **not** an employee surveillance, hiring, promotion, compensation, ranking, seniority, or personality-diagnosis tool.

## What PawSkill measures

The deterministic evaluator scores only evidence events that describe outcomes. The competency model:

| Competency | What evidence can support it |
| --- | --- |
| Problem solving | hypotheses, scoped constraints, confirmed investigations |
| Debugging | reproduction, root-cause analysis, confirmed fixes |
| Architecture | documented trade-offs, design decisions, reviewed boundaries |
| Implementation | completed changes with successful checks or review |
| Testing | focused tests, regression coverage, validation results |
| AI collaboration | AI suggestions challenged, modified, verified, or rejected |

If you've imported your Claude Code history (`npm run import:claude-history`), `npm run evaluate` also folds its observed workflow indicators (investigation before change, validation during change, iterative collaboration, test execution) into the same competencies as low-weight `observed` evidence — scored below `verified` and `corroborated` evidence, and excluded from the evidence timeline.

If you've also imported GitHub pull request history (`npm run import:git-history`), two more things happen:

- the PR delivery indicators (review approval rate, CI pass rate, test-file-change rate) become `corroborated` evidence for architecture, implementation, and testing;
- any Claude session whose activity falls within a 96-hour (4-day) window of a commit that belongs to an **approved and CI-passed** merged PR is re-graded separately and promoted to `verified` evidence. This is the one link from raw activity to a confirmed outcome the pipeline can make automatically — it's a time correlation, not proof that the specific session produced that specific PR, so it stays capped at `verified`'s weight rather than treated as certain. The window is a hand-picked heuristic (a rough stand-in for a typical review-to-merge turnaround), not a validated figure — override it with `--correlation-window-hours <n>` on `npm run evaluate` if you want to test a different value.

Sessions that don't correlate to any verified PR stay at the lower `observed` weight.

## Requirements

- Node.js 18 or later.
- `npm`.
- Optional: Claude Code CLI for live activity hooks, history import, and Claude coaching.
- Optional: Codex CLI for the alternative Codex coaching report.
- Optional: GitHub CLI (`gh`), authenticated via `gh auth login`, for pull request history import.

No package installation is currently required; the project uses Node built-ins only.

## Quick start

`npm run evaluate` only scores real, imported evidence — it has no built-in sample data. Import at least one history source first, then evaluate:

```bash
npm run import:claude-history -- --input-dir ~/.claude/projects
npm run evaluate
npm test
```

Or run that same sequence — plus git history import and local prompt sampling — in one command:

```bash
make all
```

`make help` lists every target and its override variables (`CLAUDE_DIR`, `GIT_REPO`/`GIT_AUTHOR`, `PORT`, ...). `make all` only runs steps that stay local — anything that sends data externally (`evaluate-claude`, `evaluate-codex`, `evaluate-prompting`) is a separate target you run deliberately, so a one-command convenience wrapper can't quietly bypass this project's explicit-consent design.

`npm run evaluate` reads whichever of `data/claude-history-summary.json`, `data/git-history-summary.json`, and a curated `--events <path>` file are present, and turns them into [data/profile.json](data/profile.json). If none are present, it exits with an error rather than fabricating a profile.

### After `make all`

1. **Preview the dashboard:**

   ```bash
   make serve
   # or: python3 -m http.server 4173
   ```

   Then open `http://localhost:4173`. This reads `data/profile.json` over HTTP; opening [index.html](index.html) directly as a file (or before that fetch resolves) shows a generic loading skeleton instead.

2. **Optional coaching reports** — each sends data externally, so each has its own explicit flag baked into its `make`/`npm run` command (see [Coaching reports](#coaching-reports)):

   | Command | Sends | Output |
   | --- | --- | --- |
   | `make evaluate-claude` | Derived metrics only | `data/claude-evaluation.json` |
   | `make evaluate-codex` | Derived metrics only | `data/codex-evaluation.json` |
   | `make evaluate-prompting` | Your sampled prompt text — see [Prompting-technique feedback](#prompting-technique-feedback-sends-raw-prompt-text) | `data/prompting-feedback.json` |
   | `make coach-claude` | `evaluate-claude` + `evaluate-prompting` together | Both of the above |
   | `make coach-codex` | `evaluate-codex` + `evaluate-prompting` together (prompting feedback still goes through Claude CLI — Codex isn't wired up for that call) | Both of the above |

   None of these run automatically as part of `make all` — run them only when you want that specific report.

## Typical personal workflow

Use this order for a private assessment of your existing Claude Code and GitHub history. Steps 1 and 2 are each optional, but at least one is required before `npm run evaluate` has anything to score. Steps 4–6 are optional coaching add-ons — each sends data externally and needs its own explicit flag, so run them only when you actually want that report.

```bash
# 1. Create a local, derived summary of selected Claude Code history.
npm run import:claude-history -- --input-dir ~/.claude/projects

# 2. Optional: create a derived summary of your merged GitHub pull requests
#    (auto-scoped to your own authored PRs — see "Importing GitHub pull request history").
npm run import:git-history

# 3. Generate the evidence profile from your event data -> data/profile.json.
npm run evaluate

# 4. Optional: ask Claude CLI to create a coaching report from derived data only
#    (data/claude-history-summary.json + data/profile.json, never raw transcripts).
make evaluate-claude

# 5. Optional: sample your own recently-typed prompts, locally, no network call.
npm run sample-prompts -- --input-dir ~/.claude/projects

# 6. Optional: send that sample to Claude CLI for prompting-technique feedback.
#    Unlike every other command here, this one sends your raw prompt text.
npm run evaluate:prompting -- --allow-prompt-analysis

# 7. Preview the dashboard at http://localhost:4173 (reads data/profile.json over HTTP).
make serve
```

`make evaluate-claude` is a thin wrapper around `npm run evaluate:claude -- --allow-external-analysis` (see [Coaching reports](#coaching-reports)); use `make evaluate-codex` instead if you have Codex CLI rather than Claude CLI. Every coaching/prompting command's confirmation flag is mandatory by design — it makes what leaves your machine explicit, on a per-command basis, rather than bundling it into `npm run evaluate` or `make all`.

## Evidence data and scoring

`npm run evaluate` never reads `data/sample-events.json` automatically — it's kept only as a schema example. Claude and git history imports (above) generate real `observed`/`corroborated`/`verified` evidence on their own. If you also want to hand-curate specific, narrative "verified" evidence (e.g. "fixed a latency regression, added a regression test"), copy [data/sample-events.json](data/sample-events.json) to your own file and pass it explicitly:

```bash
npm run evaluate -- --events data/my-evidence.json
```

Each evidence item should include:

```json
{
  "id": "evt_101",
  "occurred_at": "2026-08-10T10:12:00Z",
  "title": "Fixed a latency regression",
  "summary": "Used profiler evidence, rejected an early hypothesis, and added a regression test.",
  "competency": "debugging",
  "signal_score": 96,
  "verification": "verified",
  "outcome": "positive"
}
```

Allowed competency IDs:

```text
problem_solving
debugging
architecture
implementation
testing
ai_collaboration
```

Allowed verification values:

- `verified` — independently confirmed outcome, such as merged change with passing CI or a reviewed fix.
- `corroborated` — supported by more than one source but not fully independently verified.
- `observed` — activity signal only; lower weight and not suitable as a standalone performance claim.

The evaluator weights evidence by verification, reports a confidence value for every competency, and leaves a competency unscored if there is no evidence. The source is [src/evaluator.js](src/evaluator.js).

Only the top-level `events` array from a `--events` file is read. `developer`, `period`, `prior_overall`, `sources`, and `ai_collaboration` in that file are ignored — `npm run evaluate` derives the developer's name from `git config user.name`, the period label, the prior score from your last real `data/profile.json` run, and the sources list from which imports are actually present. `ai_collaboration` has no automated source yet, so the dashboard shows it as unavailable rather than inventing a number.

## Claude Code live collector

PawSkill supports Claude Code first through Claude’s supported hook lifecycle. It records local activity metadata; it does not scrape or upload session transcripts.

1. Make the `pawskill` command available from this project during development:

   ```bash
   npm link
   ```

2. Copy the `hooks` object from [integrations/claude-code/settings.example.json](integrations/claude-code/settings.example.json) into either:

   - `~/.claude/settings.json` for all your projects; or
   - `.claude/settings.local.json` for one project.

3. Start or continue a Claude Code session in that project.

The configured hooks observe only:

- session start and end;
- successful or failed `Edit`, `Write`, and `Bash` activity;
- a pseudonymous session reference and project reference.

Events are written locally to:

```text
.pawskill/claude-events.jsonl
```

`.pawskill/` is ignored by Git. A collector failure is intentionally non-blocking: it must never interrupt a developer’s Claude Code work.

### What the live collector never stores

- prompt text;
- transcript files or paths;
- source code;
- shell commands;
- tool input or output;
- environment variables or secrets;
- the actual working-directory path.

For official Claude Code hook configuration details, see the [Claude Code Hooks reference](https://code.claude.com/docs/en/hooks) and [hook guide](https://code.claude.com/docs/en/hooks-guide).

## Importing existing Claude Code history

The history importer analyses existing JSONL session files locally. By default, Claude Code normally stores them beneath `~/.claude/projects`.

```bash
npm run import:claude-history -- --input-dir ~/.claude/projects
```

It writes [data/claude-history-summary.json](data/claude-history-summary.json), which contains only counts and indicators such as:

- sessions analysed;
- number of user and assistant turns;
- reads, edits, writes, and commands;
- recognised test commands;
- investigation-before-change, validation, test-execution, and iterative-collaboration indicators;
- a per-session list of pseudonymous session references, start/end timestamps, and the same counts — kept only so `npm run evaluate` can time-correlate sessions against pull request history (see below). No file paths, prompts, or commands are included.

It does not persist raw transcripts, raw prompts, source code, file paths, shell commands, tool input/output, or hidden reasoning. Session and project identifiers are pseudonymised. The report is explicitly named `provisional_observed_practice`: it is an observed workflow summary, not a conclusion about code quality, correctness, productivity, seniority, or business impact.

When the dashboard is served locally, it displays this derived summary in a dedicated **Claude Code activity** section. It keeps those workflow observations separate from the competency profile, which continues to require independently verified evidence events — subject to the git-correlated promotion described next.

## Importing GitHub pull request history

The git importer uses the [GitHub CLI](https://cli.github.com/) to read merged pull requests. It never clones, diffs, or reads file contents — only metadata from `gh pr list` / `gh search prs`.

**By default it only imports pull requests you personally authored** — it auto-detects your GitHub login from the `gh` CLI's own logged-in session (`gh auth status`) and searches across every repo you can see, not just the one you're standing in. This matters: without this, a plain `gh pr list` in a repo returns every contributor's merged PRs, which would silently describe your whole team's delivery practice instead of yours.

```bash
npm run import:git-history
# or, to check someone else's or scope to specific repos:
npm run import:git-history -- --author octocat --owner your-org --limit 50
# to deliberately import every contributor's PRs in one repo instead of just yours:
npm run import:git-history -- --all-contributors --repo owner/name
```

It writes [data/git-history-summary.json](data/git-history-summary.json), which contains only:

- merged pull request counts;
- review approval rate, CI pass rate, and test-file-change rate;
- per-PR: a pseudonymous PR reference, merge timestamp, review decision, a derived CI pass/fail conclusion, a file-count and a test-files-changed boolean, and commit timestamps.

It does not persist PR titles, descriptions, branch names, authors, file paths, diffs, or commit messages. The report is named `verified_delivery_practice` — merged, reviewed, CI-checked outcomes are stronger ground truth than self-reported activity, but the indicators are still an aggregate across pull requests, not proof about any one specific change, so `npm run evaluate` scores them as `corroborated` rather than `verified`.

`npm run evaluate` additionally uses `commit_timestamps` from approved, CI-passed PRs to re-grade the subset of Claude sessions that fall within a 96-hour (4-day) window of one of those commits, promoting just that subset to `verified` evidence (see [What PawSkill measures](#what-pawskill-measures)). Pass `--correlation-window-hours <n>` to use a different window.

## Coaching reports

The coaching layer explains the derived evaluation and recommends a small number of habits to practise. It never computes the deterministic competency score.

### Codex CLI coaching

Run:

```bash
npm run evaluate:codex -- --allow-external-analysis
```

The command invokes Codex non-interactively with:

- the derived history summary;
- the minimised evidence profile;
- a strict JSON schema requiring `summary`, `strengths`, `opportunities`, `recommended_next_actions`, and `caveats`.

The report is saved to [data/codex-evaluation.json](data/codex-evaluation.json). Its output schema is [schemas/improvement-report.schema.json](schemas/improvement-report.schema.json).

If Codex needs access to its own local state database, run the command in a normal terminal where Codex can write to its configured state directory.

### Claude CLI coaching

Run:

```bash
npm run evaluate:claude -- --allow-external-analysis
```

Claude Code must be installed and signed in. Confirm with:

```bash
claude auth status
```

The output is [data/claude-evaluation.json](data/claude-evaluation.json). If Claude says it is not signed in, authenticate in the same terminal/user environment that runs the project:

```bash
claude auth login
claude auth status
```

Both coaching routes receive the same restricted information. Neither route receives raw Claude Code history — see the next section for the one feature that does, by explicit separate consent.

### Prompting-technique feedback (sends raw prompt text)

Every command above sends only derived metrics — counts, ratios, scores. This one is different and is documented separately on purpose: it sends a sample of your **actual prompt text** to Claude CLI so the feedback can be concrete ("this prompt didn't state an expected outcome") instead of generic.

It's a two-step, two-consent process:

```bash
# 1. Sample your own prompts locally. No network call — nothing leaves your machine.
npm run sample-prompts -- --input-dir ~/.claude/projects
# writes data/prompt-sample.json — read it before continuing

# 2. Send that sample to Claude CLI for feedback. Requires its own explicit flag.
npm run evaluate:prompting -- --allow-prompt-analysis
```

Step 1 ([src/prompt-sampler.js](src/prompt-sampler.js)) reads your Claude Code JSONL history and keeps only text you actually typed:

- synthetic turns injected after tool execution (tool results) are skipped;
- IDE-injected context tags (e.g. "the user opened file X") and Claude Code's own system markers (e.g. an interruption notice) are stripped or skipped, since those aren't your prompting;
- each prompt is truncated (`--max-chars`, default 600) and the total sample is capped (`--limit`, default 25), newest sessions first.

`data/prompt-sample.json` is written locally only — review it before running step 2. Step 2 ([scripts/evaluate-prompting.js](scripts/evaluate-prompting.js)) is gated behind `--allow-prompt-analysis`, a flag distinct from `--allow-external-analysis` specifically so it can't be triggered by habit. It sends the sampled prompts to Claude CLI asking for feedback on clarity, specificity, and stated acceptance criteria — never on your coding skill, seniority, or performance — and writes the result to [data/prompting-feedback.json](data/prompting-feedback.json).

Both `data/prompt-sample.json` and `data/prompting-feedback.json` are git-ignored, since they can contain your raw prompt text or quoted fragments of it.

## Engineering animal archetypes

The dashboard turns competency evidence into flexible engineering work-style archetypes. These are conversation starters for growth and collaboration, not fixed personality claims.

| Animal | Archetype | Work-style description |
| --- | --- | --- |
| 🦉 Owl | Investigator | Gathers context, compares signals, and turns uncertainty into testable hypotheses. |
| 🦊 Fox | Strategist | Frames ambiguity, identifies options, and chooses a path with intent. |
| 🦫 Beaver | Builder | Turns useful plans into working, maintainable increments. |
| 🐜 Ant | Validator | Notices edge cases and makes confidence measurable through validation. |
| 🐙 Octopus | Systems Thinker | Connects local changes to dependencies, interfaces, and system effects. |
| 🦡 Badger | Resilient Debugger | Persists through failures until evidence points to a real fix. |
| 🦅 Hawk | Focused Operator | Identifies the highest-value next move and finishes what matters. |
| 🐬 Dolphin | Collaborator | Makes ideas easier to share, review, and improve with others. |
| 🕷️ Spider | Architect | Builds patterns and foundations that make complex systems navigable. |
| 🦎 Chameleon | Adapter | Learns tools quickly and adjusts approach to the real context. |
| 🐘 Elephant | Steward | Protects reliability, maintainability, and the people affected by change. |
| 🐦‍⬛ Raven | Challenger | Questions defaults, tests AI output, and surfaces overlooked risk. |

The profile picks a primary and secondary archetype from competency evidence, then shows:

- two animals that are **very compatible** work-style complements;
- two animals that are **compatible** complements;
- a practice tier for each archetype.

### Avatar tiers

| Tier | Avatar identity | Meaning |
| --- | --- | --- |
| Junior | Explorer ✦ | Building the habit and learning where to look next. |
| Senior | Practitioner ◆ | Showing repeatable practice across real engineering work. |
| Master | Guide ✺ | Demonstrating broad, consistent practice in complex contexts. |

The animal stays tied to work style while its avatar frame, badge, colour treatment, and description evolve with the tier. Tiers are derived from the relevant evidence score, not from job title or years of experience. Archetype logic lives in [src/archetypes.js](src/archetypes.js).

## Privacy and responsible use

PawSkill follows a minimise-first data principle:

- Prefer structured, derived evidence to raw prompts, source code, secrets, or terminal history.
- Keep data local by default.
- Make external coaching analysis opt-in with `--allow-external-analysis`.
- The one feature that sends raw prompt text — prompting-technique feedback — requires its own separate, explicit `--allow-prompt-analysis` flag rather than reusing the derived-data one.
- Clearly distinguish verified evidence from observed activity.
- Show caveats and confidence whenever evidence is incomplete.

Do not use PawSkill reports to make employment, hiring, promotion, compensation, disciplinary, seniority, ranking, or personality-diagnosis decisions. Before adding team features, obtain meaningful consent, document retention, allow people to inspect/correct their data, and perform a privacy and fairness review.

## Verify changes

Run after modifying any scorer, collector, or archetype logic:

```bash
npm run evaluate
npm test
```

The test suite verifies evidence weighting, no-score-without-evidence behaviour, history minimisation, collector privacy boundaries, coaching output validation, and archetype tier/compatibility logic.

## Recommended next build steps

1. Replace the `gh` CLI dependency with GitHub OAuth/webhooks so PR/CI evidence can be imported without a local CLI session.
2. Correlate sessions to pull requests more precisely than a time window allows (e.g. a privacy-preserving hash match on touched file paths) so more of the `observed` tier can be responsibly promoted.
3. Add a review screen where a developer can inspect, challenge, or remove each evidence item.
4. Add user-controlled data retention and deletion.
5. Add a small local backend or encrypted data store only after the evidence model is validated.
